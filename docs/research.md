# 技术方案研究

研究范围是「聊出文章来」怎样把一个主题的聊天收成文章。结论供架构使用。本文件不包含 skill 指令，也不包含可执行脚本。

## 要解决的事

每天的学习留在零散会话里。需要按主题收成一篇文章：自己以后能翻，别人打开也能读。文章要带稳定的个人笔调，技术内容要有图，读起来不能是通用模型腔，改的时候按段改，不要每改一句就重写全篇。

## 运行环境里已经核对过的能力

这些约束来自当前 Cursor 环境里的工具定义，以及本地会话记录的文件形状。它们决定了第一版不能假设“agent 记得全部聊天”。

### 会话发现和全文不是同一个接口

`SearchConversations` 检索的是本地会话索引，外加已缓存的云端 agent 会话。它返回会话 id、标题和短摘要，不返回全文。未加引号的每个关键词都必须命中同一条会话，所以查询要短，一个主题拆成多次一到两个词的搜索。部分云端会话可能不在索引里。

全文在本机的 JSONL 里，路径形态是：

```
~/.cursor/projects/<工作区目录名>/agent-transcripts/<会话 id>/<会话 id>.jsonl
```

子代理记录在同级 `subagents/` 下。每行是一个对象，字段是 `role`（`user` 或 `assistant`）和 `message.content`。`content` 是列表，条目的 `type` 为 `text` 或 `tool_use`。抽文章只用 `text`。`tool_use` 是工具调用，留在正文里会把文章写成操作日志。

由此得到三个缺口，架构必须显式暴露，不能悄悄补全：

1. 索引命中但本机没有 JSONL 时，只有摘要，不够写文章。
2. 别的电脑上的会话、Cursor 以外的聊天，不在这套目录里。
3. 工具返回值往往不在记录里。只靠会话原文，会丢掉终端输出和网页摘录，除非用户把那些材料另存成文件。

第一版不做向量库。缺的常常是根本没同步到本机的会话，嵌入检索补不上。覆盖不够时，让用户粘贴或指定文件。

### 图的三条工具边界

| 手段 | 实际行为 | 对文章的含义 |
| --- | --- | --- |
| Mermaid | 写在 Markdown 里就能被常见渲染器显示，源文件可 diff | 结构、时序、状态、关系的默认格式 |
| draw.io（`open_drawio_mermaid` / `open_drawio_xml`） | 在编辑器里打开图，不把 SVG 写回文章目录 | 适合用户还要亲手排的图；文章仓库里必须另存源文件和导出文件 |
| `GenerateImage` | 仅在用户明确要一张图时调用；数据图表、折线、表格不走这条 | 封面、比喻图、界面示意可以；统计图不行。宽高比只有 `1:1`、`4:3`、`3:4`、`16:9`、`9:16` |

网络图片可以引用，但文章里要记下出处和许可。不把别人的长文整段抄进正文。

## 挑战一：稳定的个人笔调

形容词解决不了风格。“简洁、专业、有人味”换一篇文章就会漂。能钉住笔调的是三类可检查材料：

1. **范文片段**：两到三段本人认可的短文，起草时作为对照，而不是再抽象成口号。
2. **可观察偏好**：人称、段落大约几句、标题层次、爱用的术语和不用的术语、清单用得多还是少。
3. **从修改里长出来的规则**：用户把一句改成另一句，这个差异才是证据。

### 两条学习路径，一份档案

渐进学习和“从旧文章学”写进同一个版本化档案，避免两套风格各说各话。

- **从旧文章学**：用户指定若干 Markdown。先统计句长、标题密度、人称、标点，再由用户圈定范文片段。系统给出档案差异，用户接受后才成为新版本。
- **使用中渐进**：每一块定稿时，比较起草稿和用户接受的文本。用词替换、删掉的句式、改短的段落，记成候选规则。一篇文章结束时集中确认，不在起草中途改档案。

候选规则默认不生效。同一条偏好至少在两篇文章里出现，或被用户明确提升，才变成强制规则。一次心血来潮的改法不会变成永久法律。

### 怎么保证后面的文章还是这个人

每篇文章钉住一个档案版本号。起草和这篇的后续修订都用这个版本。档案升级只影响下一篇。这样风格可以长大，单篇文章内部不会中途换语气。

档案证据还少时，先写并审完第一节，再写后面的节。第一节是校准，不是废稿。用户如果明确说“按当前风格写完”，可以跳过这个停顿。

个人笔调和共享禁词冲突时，优先级是：这篇文章里的明确指令、私有词表、风格档案、共享禁词。用户自己的习惯用语如果撞上共享禁词，用私有词表的允许项放行。风格系统的工作是稳定本人的声音，不是把所有人改成同一种“干净文风”。

## 挑战二：图表

一张图在文章里是一等记录，和段落一样有 id、状态和源，而不是事后插进去的二进制。

按“要表达什么”选格式，不按“哪种工具最强”选：

| 要表达的东西 | 格式 | 理由 |
| --- | --- | --- |
| 流程、时序、状态、结构关系 | Mermaid 源文件，编译进 Markdown | 可 diff、可分享、不依赖编辑器 |
| 泳道、需要像素级排版、用户会反复拖 | draw.io XML，加导出的 SVG | 编辑发生在 draw.io；仓库保存导出结果，否则别人打开文章看不到图 |
| 柱状图、折线等数据图 | 由数据生成的 SVG | 生图接口明确不承担数据图 |
| 封面、比喻、界面气氛 | 光栅图，旁边放提示词文件 | 每次生成都要用户明确点头；图不能 diff，提示词负责以后重做 |
| 网上已有的图 | 本地副本加出处与许可 | 许可不清楚就改用链接，不把文件打进分享包 |

图挂在块上，不把图的字节算进段落正文。重画一张图时，只把引用它的块标成需要再看说明文字，不重写其他段落。

draw.io 目前是编辑表面。实现阶段的步骤应写成：生成或打开图、请用户导出 SVG 和 XML 到 `figures/`、核对文件在不在。不要假设 MCP 调用的返回值就是文章资产。

## 挑战三：祛除 AI 味

AI 味主要是可枚举的套话和句式，不是一种神秘的“温度”。处理分成生成时约束和写完后的检查。只做字符串替换会挖出空洞，模型再补一句，往往更假。检查命中后，重写所在句子，主张保持不变。

### 两份词表

- **共享词表**进 skill 仓库，管的是写作套话，不管行业黑话。“值得注意的是”“综上所述”“delve”“let's dive in”属于套话。“闭环”“抓手”这类词可能就是用户的职业用语，共享表里最多标成观察，不默认禁止。
- **私有词表**在用户声音目录里，三种动作：`ban` 禁用、`prefer` 改用另一个说法、`allow` 放行某条共享禁词。

词条分两种：

- **短语**：中文按子串，英文按词边界。“landscape”这类多义词放在观察级，避免误伤技术术语。
- **句式**：“不是……而是……”“不仅……更……”“Not X, but Y”。句式误伤更高，共享表里默认是观察；用户可以在私有表里升成禁用。

严重级别：

| 级别 | 起草时 | 导出时 |
| --- | --- | --- |
| `ban` | 不写 | 命中则不能导出，只重写命中的句子 |
| `watch` | 尽量不写 | 标出来，用户决定 |

建议的共享禁用起点（已写入 `skills/chat-to-article/lexicon/`）：

中文短语：值得注意的是、综上所述、总而言之、不难发现、在当今、让我们一起、本文将深入、希望本文对你、作为一个 AI。

英文短语：delve、tapestry、it's worth noting、let's dive in、in today's rapidly。

观察级（不阻断导出）：赋能、抓手、闭环、底层逻辑、leverage、robust、seamless、landscape。

这份起点已经落成 skill 里的词表文件。私有词表仍在用户的声音目录，不进仓库。

## 挑战四：按段修订，并且少重写

大范围返工通常来自三件事叠在一起：全文只有一个字符串、一句话的修改指令却把整篇放进上下文、事实和措辞绑在同一次生成里。

对应的做法：

1. **事实、大纲、正文分开。** 改措辞不动事实清单。改一条事实，只把引用它的段落标成待复核。
2. **正文按块存储。** 一块大约是用户一眼能读完的一段，或一个很短的小节。修订指令默认只带这一块的正文，加上前后块的只读文本，用来接语气。不把整篇文章放进修改指令。
3. **已接受的块默认冻结。** 邻居改了措辞，不自动把别的块打成过期。否则一次修改会级联成全篇重写。用户自己读到衔接不顺时，再点名那一块。
4. **整篇重写是单独动作**，要用户明确说，并再确认一次。普通的“这段别扭”走块修订。
5. **编译稿带块锚点。** 用户习惯直接改 Markdown。锚点还在时，改动可以收回到对应块。锚点没了，就不猜测归属，把各块原文摊开让用户指定。猜错一次等于又重写了一遍。

块的目标长度放进风格档案（建议中文一段大约 80 到 280 字），因为“一段”的手感因人而异。

## 分享

分享出去的是编译后的文章和它的图，不是聊天记录，也不是风格档案。默认导出去掉会话 id 和块锚点。出处附录由用户另选打开。

分享前做两道检查：禁用词是否还在，以及明显的密钥、令牌、连接串。密钥只标记，不静默删掉主张，避免用户不知道少了一条材料。项目代号、未公开的人名交给用户在清单里确认，正则覆盖不了。

## 建议采用的路线

采用“主张账本 + 块正文 + 版本化声音档案 + 词表检查”。会话检索是入口，粘贴和文件是同等的材料来源。图以可编辑源文件为准，光栅图是例外。

不采用的做法：

- 把整段聊天一次生成一篇 Markdown，再靠追问润色。这就是现在返工大的原因。
- 把风格写成一段系统提示里的形容词，没有版本、没有范文。
- 用生图接口画架构图和数据图。
- 在第一版建聊天向量库，或依赖 draw.io 自动把图写回仓库。

## Demo 落地了什么

`skills/chat-to-article/` 里有 skill 指令、共享词表，以及抽取、扫描、编译、锚点同步和风格钉住的脚本。判断、起草和改写仍由 agent 按这些指令完成，不写进脚本。
