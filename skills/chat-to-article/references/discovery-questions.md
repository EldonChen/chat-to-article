# 发现式提问：只在关键分岔口向用户提问

人与 Agent 的协作是写作过程的一部分，但提问是为了解决**真正会改变文章走向的未知项**，而不是让用户填一份冗长的问卷。

## 提问原则

1. **先从追问轨迹和已有材料里找答案**：
   - 用户在原始聊天里的提问序列已经暴露了他的困惑起点、关注重点和核心结论。能从对话材料中直接归纳出的写作动机、目标读者和行文方案，直接填入计划草案交用户确认，不要重复盘问。
2. **一次只问最关键的 1–3 个分岔问题**：
   - 优先给出带推荐项（及简短推荐理由）的选择题，并提供“暂不确定 / 按推荐继续”和自定义输入兜底。
   - 若当前环境有 `ask_questions`（或宿主提供的结构化提问工具如 `AskQuestion` / `request_user_input_async`），优先调用工具呈现，并在发出问题后等待用户回复。
3. **区分硬约束与软偏好**：
   - 事实边界、保密要求、目标受众属于影响内容取舍的关键项；
   - 语气冷暖、句式节奏属于软偏好，与其抽象提问，不如在第一块试写时出多版样稿让作者直观挑选。

## 六幕讲解，标题是路标

科普正文按 [SKILL.md](../SKILL.md) 的六幕写。大纲标题 12～22 字，只写层级和问题。判断放在该节第一句黑体里。禁止用「我一开始以为」或半截引语当标题。

1. **读者正在做的事**。开篇不要硬开场。先预设读者正在做的事，例如在做大模型应用，要从大量文本里按业务格式抽出数据。再点出这个能力已经被接口收成一个字段，并用一句把张力立住：从生成原理看这本不该成立，眼前是工程技巧。然后才是一次失败。坏输出是模型真正先说出口的那句寒暄，解析器停在第一个字符。并排代码块就是这次失败：左侧带导语，右侧是去掉导语后的合法对象，取值用材料原值。第 1 幕正反例的数据格式必须与首个状态表的起始符号一致。然后是最多 4 条的故障短列表，再是定义、两组输出和主线问题。
2. **普通逐词生成**。前缀、全词表分数、全词表概率、采样接回前缀，并说明为什么「按格式输出」在原理上站不住。未加掩码的表带省略号，摘出来的概率不许加成 1。这一节不写拦截。
3. **按语法位置掩码**。每张表前先写前缀到了哪。第一张与开篇同一个起始状态，解析器要的结构 token 留在允许集里。材料里已经有原始打分的每一个状态都算完一整张表，不能只报允许集的名字。材料中的每个状态机都要有自己的一段。每个状态只用同一次的数，不在表旁写「这不是同一次打分」。然后才回答改权重、写完再改、以及先取 top-k 为什么不行。
4. **文法引擎**。状态机和工程优化：为什么不必对每个 token 做完整解析，以及正则 / 有限状态、上下文无关文法 / 栈、Schema 编译文法这三行能力对比。节末的问句是：如果第一个 token 的允许集合本来就很大，而不像对象那样只能从一个固定的起始符号开头，这套还怎么成立。
5. **语法不等于答案**。先回答上一幕那句问话。两个递进反例之后，才挂模型偏好、文法允许集、任务答案这三个集合。
6. **收束**。五层表，一句黑体回答「解析通过之后还要补上哪一层」，再加最多四行编号路标。

材料里没有的数不要编，也不要在正文里解释缺了哪一项。反例必须来自材料。材料里没有的极限，留在 `knowledgeGaps`，不要另编一个实验。

## 常见分岔问题示例

### 文体与切入角度
> 这篇文章你更希望读者把它当成哪一种？我推荐 **追问复盘式工程文章**，因为现有聊天完整记录了从踩坑困惑到拆解机制的过程。  
> A. 追问复盘式工程文章（推荐）　B. 面向新手的分步教程　C. 偏原理的机制解析　D. 其他

### 目标读者定位
> 主要写给谁看？  
> A. 遇到过类似痛点的同行工程师（推荐，保留技术细节）　B. 刚接触该概念的学习者（补充前置概念）　C. 关注选型与边界的技术负责人
