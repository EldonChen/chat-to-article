# 写作计划：先决定写什么，再决定怎么写

文章生成不是从主题直接跳到大纲。写作前先建立一个短小的“文章契约”，把方向性选择显式化。它用于引导主张筛选和结构设计；主张仍需逐条确认，大纲仍需单独确认。

## 四个决定

### 1. 文体与作品类型

确定读者会把它当成什么来读，以及这种类型对内容有什么要求。可参考：

- 科技 / 工程文章：技术解释、实践记录、架构决策、教程、故障复盘、设计论证。
- 学术与研究写作：研究论文、综述、观点文章、研究札记；声明证据边界、方法和引用要求。
- 人文社科写作：概念辨析、历史脉络、批评、论证性随笔、田野或案例研究。
- 叙事写作：小说、回忆、纪实叙事；明确视角、时间线、人物和事实边界。
- 面向大众的解释 / 评论 / 专栏 / 操作指南等。

类别可组合，也可由用户自定义。不要仅凭“技术主题”就默认写成教程或论文。若用户指定投稿刊物、平台或系列，先查其实际格式要求并遵循。

### 2. 读者与目的

用一句话描述主要读者、他们已有的知识，以及读完后希望他们理解、相信、感受或采取什么行动。读者不清楚时，优先确定“主要写给谁”，不试图同时照顾所有人。

### 3. 写作偏好：用轴和锚点，不贴标签

风格是模糊且随场景变化的。把偏好记为连续倾向或两端之间的位置，允许“中间”“看情况”“举例再定”。只确认这篇文章相关的维度：

| 维度 | 一端 | 另一端 |
| --- | --- | --- |
| 解释节奏 | 先给结论 | 先铺背景再揭示结论 |
| 抽象程度 | 原理和概念 | 具体案例和操作 |
| 论证姿态 | 谨慎、限定结论 | 鲜明、直接表达判断 |
| 叙述视角 | 第三人称 / 客观说明 | 第一人称 / 亲历叙述 |
| 读者假设 | 领域新手 | 领域从业者 |
| 结构显性度 | 连贯散文 | 明确标题、步骤和清单 |
| 语气 | 克制、正式 | 口语、亲切 |

不要要求用户一次填完所有维度。优先取用已钉住的个人声音档案；只问当前文章中会影响取材、结构或第一节写法的未知偏好。语气和笔调不必在计划阶段问清：第一块会按 [voices.md](voices.md) 出多版让作者挑，看着样稿选比回答抽象问题准确。选定后写入 `writing-plan.json` 的 `voice` 字段（由 `pick-variant` 写，不要手填）。

### 4. 行文方案

在已有材料基础上选一个主要推进逻辑，并说明为什么适合这篇文章。可选方案不是固定模板：

- 问题 → 约束 → 方案 → 取舍 → 结果 / 经验（工程实践）。
- 现象 → 概念 / 背景 → 证据 → 解释 → 意义与边界（解释或分析）。
- 主张 → 理由 → 证据 / 例子 → 反例或限制 → 结论（论证）。
- 时间 / 事件 → 转折 → 后果 → 回看（叙事）。
- 任务 → 前置条件 → 步骤 → 验证 → 故障处理（教程）。
- 研究问题 → 方法 → 结果 → 讨论（适用时；不要强套到非实证文章）。

行文方案要能解释章节之间的因果或认知推进，而非只列标题。确认写作计划后，才从已选材料中抽取主张；确认主张后再把方案展开成章节大纲。证据不足时标出缺口，不让流畅结构掩盖缺失证据。

## 写作计划文件

在文章目录写入 `writing-plan.json`，只记本篇需要的决定。示例：

```json
{
  "status": "confirmed",
  "genre": ["工程实践文章", "解释性文章"],
  "audience": "熟悉后端开发、不了解本项目存储设计的工程师",
  "purpose": "解释按块修订如何限制文章返工，并说明取舍",
  "styleAxes": {
    "explanationPace": "先具体问题，再给原理",
    "abstraction": "案例略多于概念",
    "stance": "直接但标明适用边界",
    "structure": "小标题清楚，正文保持连贯"
  },
  "approach": "从一次改动范围失控的具体问题出发，说明块模型、展示修订流程，再讨论限制。",
  "openQuestions": []
}
```

用户还没决定的偏好可以保留在 `openQuestions`；只要它不阻碍材料收集，就不必强迫定案。`status` 设为 `confirmed` 表示用户认可当前方向，不代表每个风格轴都已有答案。方向实质改变时，先改计划、说明影响，再重新确认受影响的大纲；不要暗中切换文体。

## 参考依据

这些方法归纳自公开写作规范，作为启发而非统一标准：Purdue OWL 将写前思考组织为目的、读者、文体、语气和所需证据；Google 与 Microsoft 的开发者写作指南强调面向明确读者、结构清楚和一致语气；Diátaxis 区分教程、操作指南、参考和解释，因为它们服务不同读者任务；Nature 的文章类型指南展示了研究论文、简讯等类型具有不同结构要求；Stripe 工程文章常以实际约束和具体决策串起架构说明与经验。
