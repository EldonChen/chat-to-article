# 写作计划：先从追问还原动机，再决定写什么与怎么写

文章生成不是从主题直接跳到大纲，也不是让用户凭空填写一张抽象问卷。用户在聊天里的**主动追问过程**本身就是他理解这个主题的认知过程。写作前先从追问序列中还原「结构化写作动机（`motivation`）」，再建立一个短小的“文章契约”，把方向性选择显式化。

## 一、从追问轨迹提取结构化写作动机（`motivation`）

阅读会话中的用户提问序列（以及 AI 的回答如何触发了下一轮追问），由你（Agent）直接通过语义理解提炼以下五项，并记录在 `writing-plan.json` 的 `motivation` 字段中：

| 字段 | 含义 | 从哪里识别 |
| --- | --- | --- |
| `initialConfusion` | **困惑起点**：作者最初卡在什么具体场景、痛点或直觉冲突上 | 会话开头的提问、报错经历或直觉疑问（`trigger`） |
| `inquiryJourney` | **追问演进链**：作者在对话中一步步追问的关键节点（`turn`、`question`、`intent`、`shift`） | 用户连续追问序列（`trigger` 初始提问、`probe` 深入追问、`counter` 认知碰撞/反问、`synthesis` 归纳收敛）及每轮带来的认知推进 |
| `ahaMoment` | **核心顿悟**：追问到最后真正想通的核心判断 | 用户自己复述确认的句子，或对话收敛出的核心洞察 |
| `knowledgeGaps` | **待补认知缺口**：聊天时一笔带过、尚未验证或缺少边界条件的地方 | 会话中未展开的追问、条件限定或需要在写作时补齐的证据 |
| `readerValue` | **读者共鸣价值**：处于相似困惑起点的读者顺着这条路径读完能收获什么 | 由 `initialConfusion` 到 `ahaMoment` 的认知跨越推导 |

有了 `motivation`，就能自然推导出 `purpose`（为了解答什么疑问、传递什么顿悟）和 `approach`（如何顺着作者的追问爬坡路径带领读者理解），让作者自己看得懂、能判断好坏，也让读者读起来有真实的思考脉络。

作者的追问链不要原样变成小节标题。聊天里的第二问常常已经站在术语里面，读者还在场景外面。

## 一点五、读者侧的六幕

科普文章在 `writing-plan.json` 里写下读者要走的六幕，而不是只归档作者当时怎么问。大纲标题 12～22 个字，只写层级和问题。判断写在该节第一句，不写进标题。

| 幕 | 读者读完能回答什么 | 写作时怎么用 |
| --- | --- | --- |
| 1 读者正在做的事 | 这件事为什么重要，这项技术是什么 | 开篇对着读者讲。先写这份材料里读者正在做的一件具体的事，再点出它在产品表面上已被收成一个开关，然后用这份材料自己的矛盾立住张力：从底层原理看，这件事不该显得这么省事。不要套用别的题目的场景或结论。这句之后才写一次失败：输入、模型真正先说出口的那句寒暄、下游停在这句话的第一个字符。并排的两份代码块就是这次失败：左侧带导语，右侧是去掉导语后的合法对象，取值用材料原值。第 1 幕正反例的数据格式必须与首个状态表的起始符号一致。再用最多 4 条短列表带出其余故障。然后是定义、同一输入的两组输出、主线问题 |
| 2 普通逐词生成 | 没有约束时，下一个词从哪来 | 先补理解后面机制所必需的基础。四步：前缀、全词表实数分数、全词表 Softmax、采样并接回前缀。未掩码表只照搬源材料中同一状态下的原始候选与全词表概率，末行加省略号。严禁把摘出行加成 1，也严禁并进后一个状态的候选 |
| 3 掩码改写概率 | 约束插在哪一步，两个笨办法为什么不行 | 每张表前先写明当前前缀推进到的语法位置。材料里已经有原始打分的每一个状态都列完整张掩码表，写出谁变成负无穷、谁留下、概率是多少。只报允许集的名字不算完成。每个状态只用同一次的那一排数。多个有限分数都留下并在这些分数上重新归一化，而且必须配上算完的行：哪些留下、哪些变成负无穷、重算后的概率各是多少。材料里已经给过原始打分的状态，每个状态一张表。只报允许集的名字不算完成。掩码改了分数时，同一张表写出改完之后的概率，只从仍然有限的分数来算。只说「会重新归一」不算完成。表头若是改写后的分数，格子里必须是那个分数。只留下一个 token、材料又没有原始分数时，写明材料没有这个数，概率为 1 是因为只剩一个有限项，不要把「留下」写进分数列。不要拼上另一组分数，也不要写「这不是同一次打分」。材料没有为某枚 token 写分数时，写明它没有分数，不要把别的 token 改名填进「留下」列。然后才回答：推理时拦截，不是改权重，也不是写完再改；不能先取 top-k |
| 4 文法引擎 | 十万个 token 如何被检查，三种引擎各锁住什么 | 能力对照和放行名单是两件事，名单不能代替对照。对照写清：只能记有限状态的机器、带栈的文法、由类型约定编译出来的规则，各自锁得住哪一种失败。节末问句从材料里还没合上的缺口来，不指定成某一个固定问题 |
| 5 语法不等于答案 | 为什么每一步都合法，任务仍会失败 | 顺着材料里的下一问往下走。若这里指出某种文法仍放行前表写成负无穷的 token，同一段写明前表是哪一种机器做的。两个递进反例：过宽文法放行的导语，类型合法但荒谬的值。类型已通过、值仍不成立时，图上要看见那个值为什么还过得去。然后才挂三个集合 |
| 6 收束 | 解析通过之后还要补上哪一层 | 用读者能带走的层次图回答开篇的问题。每一层只写保证什么、不保证什么。只点出集合的名字不能代替这张图。图后一句黑体回答开篇问题，再加最多四行编号路标。不要用六幕复述代替这句判断 |

大纲里每一节再落两个桥字段：

- `bridgeFromPrev`：本节第一句接住的上一节问题。第一节接主线问题。
- `hookToNext`：本节最后一句，必须是通顺的问句。末节交回开篇那组输出，写明它被锁在哪一层。

同一份计划里，未加掩码的 `mechanismTrace` 记录全词表概率和省略号，不把摘出来的几行加成 1。每一段掩码的 `mechanismTrace` 先写 `state`：前缀已经写下哪一个 token、当前在等什么。起始状态与开篇是同一个位置，解析器要的结构 token 留在允许集里。材料里已经有原始分数的每一个状态各自单独一段，`mapping` 把该状态同一次的行算完，不能只写允许集的名字。材料里已经出现的每一台状态机、每一次状态转移、每一份按状态给出的允许集，计划里都要有对应的一段讲解，不能只留表，也不指定落在哪一幕。多个有限分数都留下，并在这些分数上算出改完之后的概率写进 `after`，行里要有谁留下、谁变成负无穷、概率是多少。材料写明只留下一个 token、材料又没有原始分数时，`after` 写 1，并注明材料没有这个原始分数、概率为 1 是因为只剩一个有限项；分数列不要写「留下」。只写「会重新归一」不算完成。材料没有分数的 token 不要改名后填进留下的那一列。禁止把不同状态或不同一次的分数并进同一段，也禁止自造分数，正文也不写「这不是同一次打分」。补不齐的数记在 `knowledgeGaps`，正文不解释缺了哪一项。

每张图在计划里记 `textFallback`：图下那个代码块或小表要写出的左右或前后差异。正文先确认 `figures/<id>.svg` 已落盘，再写相对路径，并把 `textFallback` 放在图片正下方。

`capabilityContrast` 写三种约束机器各自锁得住哪一种失败：只能记有限状态的机器、带栈的文法、由类型约定编译出来的规则。放行名单不能代替这张对照。`acceptanceLayers` 写读者能带走的层次图，每一层只写保证什么、不保证什么。两张表不能并成一张，集合的名字也不能代替层次图。

`extendedMetaphor` 可省略。若填写，只能是机制算完后的半句。

形式化符号写在第五幕的两个具体输出之后。同一段新符号不超过 3 个。正文不出现「聊天里」「对话中」「摘录里」「聊天没有」「聊天写到」，也不出现「没有给出」「没有在同一次计算」「确定得了……确定不了……」。

## 二、四个方向性要素

### 1. 文体与作品类型（`genre`）
确定读者会把它当成什么来读，以及这种类型对内容有什么要求：
- 科技 / 工程文章：技术解释、实践记录、架构决策、教程、故障复盘、设计论证。
- 学术与研究写作：研究论文、综述、观点文章、研究札记；声明证据边界、方法和引用要求。
- 人文社科写作：概念辨析、历史脉络、批评、论证性随笔、案例研究。
- 叙事写作：纪实叙事、回忆、项目故事；明确视角、时间线与事实边界。

类别可自由组合，也可由用户自定义。

### 2. 读者与目的（`audience` & `purpose`）
用一句话描述主要读者、他们已有的知识背景，以及读完后希望他们理解、相信或能够采取什么行动。

### 3. 写作偏好轴（`styleAxes`）
把偏好记为连续倾向或两端之间的位置，只记录与本篇相关的维度（空着表示不限定）：

| 维度 | 一端 | 另一端 |
| --- | --- | --- |
| `explanationPace`（解释节奏） | 先铺背景再揭示结论 | 直接先给结论 |
| `abstraction`（抽象程度） | 从具体案例和操作出发 | 从原理和概念框架出发 |
| `stance`（论证姿态） | 谨慎克制、限定结论边界 | 鲜明直接表达判断 |
| `perspective`（叙述视角） | 第一人称亲历叙述 | 第三人称客观说明 |
| `readerAssumption`（读者假设） | 面向领域新手 | 面向领域同行 |
| `structure`（结构显性度） | 连贯散文叙事 | 模块化小标题与步骤清单 |
| `tone`（语气） | 正式克制 | 口语亲切 |

具体笔调（`voice`）不必在计划阶段抽象盘问，可在首块试写时出多版样稿让作者直观挑选（见 [voices.md](voices.md)）。

### 4. 行文方案（`approach`）
在已有材料和追问轨迹基础上选一个主要推进逻辑：
- **追问爬坡式**：困惑起点 → 追问转折 → 核心机制 → 边界与代价（最贴合主动学习过程）。
- **工程决策式**：问题 → 约束 → 候选方案 → 取舍 → 结果与经验。
- **原理解析式**：反直觉现象 → 概念/背景 → 证据与机制 → 意义与边界。
- **论证式**：核心主张 → 理由与证据 → 反例或限制 → 结论。
- **操作指南式**：任务目标 → 前置条件 → 步骤 → 验证与故障处理。

## 三、产物格式（`writing-plan.json`）

在文章目录 `articles/<slug>/writing-plan.json` 中保存（可通过 `review_writing_plan` 工具由用户审阅确认后自动写入，也可直接写入）：

```json
{
  "status": "confirmed",
  "genre": ["工程实践文章", "解释性文章"],
  "audience": "熟悉后端开发、不了解本项目存储设计的工程师",
  "purpose": "解释按块修订如何限制文章返工，并说明取舍",
  "styleAxes": {
    "explanationPace": "先具体问题，再给原理",
    "abstraction": "案例略多于概念",
    "stance": "直接但标明适用边界"
  },
  "approach": "从一次改动范围失控的具体问题出发，顺着追问过程说明块模型与图资产管理，再讨论限制。",
  "openQuestions": [],
  "motivation": {
    "initialConfusion": "只想换掉文章里的一句话，为什么每次交给 AI 都会把整篇重写？",
    "inquiryJourney": [
      {
        "turn": 1,
        "question": "我改文章时最烦的是，只想换一句，整篇都被重写。",
        "intent": "trigger",
        "shift": "正文按块独立存储，修订时只提交目标块，相邻块仅作只读上下文。"
      }
    ],
    "ahaMoment": "将主张、大纲与正文块解耦，才能把每次修改严格限制在单块内。",
    "knowledgeGaps": ["用户在编译稿里直接改字时如何按锚点安全收回"],
    "readerValue": "帮助同样受困于 AI 改稿返工的工程师掌握按块隔离上下文的做法。"
  },
  "openingArc": {
    "scene": "夜里只想把第三段一个词换掉，稿子回来时例子和结尾一起没了。",
    "suspense": "明明叮嘱过「别的地方别动」，它为什么还能改到别的段落？",
    "bridge": "先看它手里拿着的是整篇稿，还是单独的一块。"
  },
  "questionLadder": {
    "phenomenon": "只改一句，整篇的例子和语气都变了。",
    "anomaly": "舒服的解释是「提示词没写严」。把「别的地方一个字都不许动」写到最严，整篇仍会被重写。",
    "principle": "生成是在重写它看见的全部上下文；修改权要在递交的文本范围上收回。"
  },
    "goldenThread": "修改范围等于这次提交的那一块。提示词里的「别动别处」改变不了模型看见的上下文。",
    "mechanismTrace": {
      "input": "只提交这一块的正文，邻块只放在只读上下文",
      "state": "待写回的范围",
      "mapping": "未点名的块不进入写回",
      "after": "修改范围等于这次提交的块",
      "invented": false,
      "source": "本示例的块修订说明"
    }
}
```

用户尚未决定的细节可留在 `openQuestions` 中，不必强行阻塞后续写作。

上面这份示例讲的是按块修订。科普另题时，`openingArc.scene` 先只写一次翻车，坏输出是模型先说出口的那句寒暄，其余故障放在短列表里，然后再写定义和两组输出。掩码表的 `state` 要写明前缀已经到了哪。大纲标题 12～22 字。末节是五层表、一句黑体判断，以及最多四行路标。示例里的块修订句子不要搬进另一篇文章。
