# 聊出文章来（chat-to-article）

本 Skill 采用**声明式设计**：这里定义可用的上下文资源、目标产物的形态与核心约束，以及面向不同场景的推荐路径。你（Agent）根据用户的实际意图与材料成熟度自主规划步骤、直接读写产物文件或调用交互式 UI 组件，无需遵循僵化的程序化状态机。

---

## 核心理念：追问即认知，以写促学

用户在聊天里的**主动追问过程**，本身就是他理解一个概念的认知过程。不要把聊天记录仅仅当成扁平的静态语料池去硬凑摘要，而要从用户的连续提问中感知他的认知爬坡轨迹：

1. **困惑起点（`initialConfusion`）**：最初在什么具体场景、痛点或直觉冲突上卡住了？
2. **追问演进链（`inquiryJourney`）**：哪几轮追问（「为什么不直接…」「可是如果…」）打破了原有直觉、把思考推向深处？
3. **核心顿悟（`ahaMoment`）**：追问到最后真正想通的核心判断是什么？
4. **待补认知缺口（`knowledgeGaps`）**：聊天中哪些地方只是聊爽了但还缺严谨证据、边界条件或反例？

将这套**写作动机**融入成文过程：一方面借助写作的严密性帮助作者补齐聊天时跳过的缺口（加深作者自身的结构化认知）；另一方面顺着作者亲历的认知坡度组织章节（而非全知视角的教科书平铺），让处于相似困惑起点的读者自然读懂，形成正向飞轮。

动机是原料，不是章节顺序。面向大众的科普要另写一份**六幕推演契约**，记在 `writing-plan.json`。文章是讲给读者的结构化讲解。小标题是知识树路标：12～22 个字，点明这一节的原理层级和要回答的问题，短到只看目录就能数出整棵树。完整判断放在标题下的第一句，用黑体。禁止用半截话当标题，例如「我一开始以为，得分清零就是答案」。也禁止把一整句结论塞进标题。

正文按下面六幕写完，不能跳幕，也不能在第六幕之前停笔。凡是要写「全词表分数、分数变成概率、采样」的小节，必须排在第 2 幕之后。第 2 幕结束之前，正文不出现掩码、负无穷、拦截时机。

**展开顺序固定为三层，六幕落在这三层里，不能跳层。** 第一层只讲不带约束的生成原理，并说明为什么「按格式输出」在原理上站不住。第二层再讲掩码、状态机，以及怎么把当前允许集算得足够快。第三层才用读者会问的那一句往下走：如果第一个 token 的允许集合本来就很大，而不像对象那样只能从一个固定的起始符号开头，这套还怎么成立。

1. **痛点特写与问题全景。** 开篇对着读者讲，不要硬开场。先预设读者正在做的事，例如在做大模型应用，要从大量文本里按业务格式抽出数据。再点出这个能力已经被接口收成一个字段。然后用一句把张力立住：从生成原理看，按格式交出结构本不该成立，读者眼前看到的是一套工程技巧。这句之后才落到一次已经发生的翻车，而且只用这一次：当时的输入、交回来的坏输出、下游在哪一个字符或哪一行接不住。用「你」称呼读者。坏输出必须是材料里模型真正先说出口的那句寒暄导语，解析器停住的字符就是这句话的第一个字符。不要把打分表里单独一个英文 token 当成模型交回的全文。开篇解析器当时要的那个结构 token，必须在第一张掩码表里留在允许集中，并按同一个起始状态处理被拒绝的那个 token。不要在开篇里把几类故障轮流演完，也不要用「开发者把……」起句。紧接着用不超过 4 条的短列表点出其余典型故障，每条一行。然后再用直白的话定义这项技术，给出同一输入的两组输出，并用一句话写下全文主线问题。这两组并排的代码块必须就是刚才写下的那次失败：左侧是带上那句废话导语的坏输出，右侧是去掉这句导语之后、材料里这道请求要的合法对象。字段取值只用材料里已经出现的原值，不要换成后文另一组例子，也不要改材料里的数字。
2. **第一层原理：没有约束时，下一个词怎么来。** 这一幕只讲普通自回归：已有前缀进入模型；最后一层对整个词表打出一排实数分数（logits，词表大约十万维）；Softmax 把这些分数变成概率；按这个分布取出下一个 token，接回前缀。配一张**没有掩码**的打分表。未掩码表只照搬源材料中同一状态下的原始候选与全词表概率，末行加 `...` 代表其余词表。严禁将摘出行自行归一化为 1，也严禁跨状态混拼其他状态的候选或自造数字。这一幕还要说清为什么「按格式输出」在原理上站不住：模型只是在全词表上为下一个 token 打分，并没有一个按业务格式书写的内部结构。这一幕不写掩码、负无穷，也不回答「改不改权重」。
3. **第二层原理：约束插在分数和概率之间。** 每张掩码表前先写明当前前缀推进到的语法位置：还在整段开头，还是已经写下起始符号、正在等下一格。允许集换成后一个状态之前，必须先写出前缀前进了哪一个 token。开篇那张掩码表与开篇是同一个起始状态、同一种序列化：解析器拒绝的那个 token 被写成负无穷，解析器当时要的结构 token 留在允许集里。第 1 幕正反例的数据格式必须与这张表的起始符号一致。导语里的字若没有和该起始符号出现在同一次打分里，就不要焊成一张新表；第一张掩码表只用未掩码表里已经有的行。材料里已经给出原始打分的每一个语法状态，都要另列一张完整掩码表，不能只报允许集里有哪些名字就跳过。材料里有几份原始打分，就有几张表，每一行写明谁被改成负无穷、谁留下、Softmax 之后概率是多少。掩码表不能代替讲解：材料里已经出现的状态机、状态转移，或按某个状态给出的允许集，各自要有自己的一段，写清当前在等什么、接受下一步之后转到哪里、允许集里留下什么。材料中的每个状态机都要有自己的一段。每个状态只用材料里同一次给出的那一排数，一张表一步算完。这一步有两个以上 token 仍是有限分数时，这些行都留下，并只在这些有限分数上重新归一化。只留下一个 token 时，它的概率是 1。不要把别的轮次的概率和另一组原始分数拼在旁边，也不要写「这不是同一次打分」。这些表都算完之后，才回答两个直觉问题：这是推理时的实时拦截，不是改训练权重，也不是整段写完再改；不能先取 top-k 再过滤，因为合法 token 可能根本不在短名单里。
4. **第三层原理：允许集怎么算出来。** 用「看到这儿你可能会问」把问题交给读者：词表有十万个 token，难道每一步都对每个 token 跑一遍完整解析？由此展开预编译的语法状态和工程上的优化，以及一张独立的能力对比表：正则 / 有限状态自动机、上下文无关文法 / 下推自动机、JSON Schema 编译成的文法。列是机制层级、用什么数据结构、能锁住什么、锁不住什么。这张表不并进后面的验收分层。材料里每一台状态机在这一幕也要有自己的一段，不能只剩对比表。节末把第三层的那句问话交给下一幕：如果第一个 token 的允许集合本来就很大，而不像对象那样只能从一个固定的起始符号开头，这套还怎么成立。
5. **第四层原理：语法合法仍会答非所问。** 用上一幕留下的那句问话起头，先回答它，再翻过来：每一步都落在文法允许的集合里，任务仍可能失败。用材料里的两个递进反例，并先指认再挂符号。一个是第一步的允许集合已经很大，一句导语本身就能留下来，而且比任务要的那个结构概率更高。一个是类型已经锁死之后，一个整数仍然可以在业务上荒谬。三个集合的关系是：模型偏好、文法允许的集合、任务真正要的答案。同一段新符号不超过 3 个。
6. **收束：解析通过之后还缺哪一层。** 不能停在某一个反例上。先用一张五层表：语法生成（逐步掩码）、结构契约（Schema / 类型）、业务语义校验、把用户那句话编译成窄契约、执行前的安全检查。每一层写它保证什么、不保证什么。表后面先用一句黑体回答开篇的主线问题，并写明：输出已经能解析、结构也通过之后，还要补上哪几层才算这道题答对。然后再用不超过四行的编号路标，从普通逐词生成收到五层防护。不要把六幕再写成一段复述。结尾可以出现「综上所述」，但不能只剩这四个字。

小标题可以长成这样（判断仍在下一句黑体里，不进标题）：`第一层原理：大模型怎样逐词生成？`、`第二层原理：负无穷掩码改写哪一步？`。

**段间桥。** 上一节最后一句必须是读得通的问句，交给下一节。写完朗读一次。读不成问句就改掉，不要为了短，把「还没回答的两件事」写成「已经做掉的事」。下一节标题下的黑体导语先用「你」或「我们」接住它，例如「顺着这个思路往下想……」「看到这儿你可能会问……」。不要写「读者接着会问」「开发者把」。

**对着读者讲。** 正文是一次共同追查。开篇先落到读者正在做的事上，不要用翻车硬开场。每一幕的入口和反转，都直接对「你」说。机制句的主语仍是模型、分数、token 和语法状态，温度放在过渡上，不放在比喻上。

**成稿通读。** 每一段写完就通读一遍。句子要能单独读通，不能把几个动词拼在没有宾语的壳子里。例如「两张表都算完，你可能会追问两件事先做掉的事」是病句。交给下一节的那句要改成读得通的问句。重复啰嗦的半句删掉再往下写。

**同一个案例贯穿。** 开篇那一组输入、字段和取值用到结尾，取值保持材料里的原值。第 1 幕正反例的数据格式必须与首个状态表的起始符号一致，不要一种序列化的正文配另一种序列化的起始符号。开篇左右两份代码块就是第一句那次失败和去掉导语后的合法对象，不要换成后文才出现的另一对输出。把格式放宽成另一种序列化时，先写一句「现在把格式放宽成……」，代码块再跟着换。不要中途换成另一组没铺垫的名字。

**画面一句。** 每张表前面用一句话给一个屏幕：光标停在哪个字符，下一格在等什么。表后面用一句话说明屏幕上刚改了什么。三张状态表之间要换气，一句只推进一个动作。这是画面，不是比喻：主语仍是字符、token 和分数。

**比喻不能当主语。** 主语是模型、分数、token、语法状态、Schema、验证器。生活隐喻最多在该步算完后用半句，删掉仍不影响推演。柜台、申报表、柜员、盖章、落笔、换油墨一旦成了主语，这一维记 0 分。

**成稿不打破第四面墙。** 正文禁止「聊天里」「对话中」「摘录里」「摘录没有」「聊天写到」「聊天没有」「聊天后文」。出处只放在计划的 `source` 和 `knowledgeGaps`。

**表旁不写缺数。** 数值表不留空单元格，不解释「没有在同一次计算」「没有给出」「这不是同一次打分」「确定得了……确定不了……」。一个状态只放一张能一步算完的表。一行算不完就不要进这张表。详见 [style.md](references/style.md)。

**图是双保险。** `figures/*.svg` 先落盘。写链接之前按 UTF-8 读出至少一处图内文字，确认文件在、文字没乱码。然后才写相对路径。交稿前逐条打开 `article.md` 里的 `](./figures/`：磁盘上打不开的链接删掉，只留图解框。详见 [figures.md](references/figures.md)。

## 一、可用资源（Resources）

### 1. 对话与材料来源
- 本地会话记录（JSONL）、导出的对话文件（如 `exports/<share-id>.json`）、用户指定的笔记文件或直接粘贴的文本。
- 会话检索、分页完整性核对与文本抽取方式见 [sources.md](references/sources.md)。

### 2. 个人声音目录（Voice Home）
路径为 `$CHAT_TO_ARTICLE_HOME`，未设置时默认为 `~/.chat-to-article/`（与具体文章目录隔离，分享文章时不会泄露个人词表）：
- `profile.json` 与 `history/r<N>.json`：版本化的个人风格档案与历史快照（见 [style.md](references/style.md)）。
- `exemplars/`：作者认可的本人范文片段。
- `lexicon/private.json`：个人禁用词、偏好替换词与放行词条（见 [lexicon.md](references/lexicon.md)）。
- `candidates.jsonl`：从日常改稿中收集、待升级进全局档案的风格候选规则。

### 3. 内置词表与笔调参考
- `<skill>/lexicon/`：共享的中英文套话与观察句式词表（见 [lexicon.md](references/lexicon.md)）。
- `<skill>/styles/presets.json`：内置笔调样稿，供作者尚未建立个人档案或想尝试不同文风时选配（见 [voices.md](references/voices.md)）。

### 4. 可选的交互式 UI 组件（MCP Apps）
当本轮工具清单中存在 `review_writing_plan`、`review_claims`、`review_outline`、`review_variants`、`review_block`、`review_figure`、`review_style_candidates`、`ask_questions` 时，可按需调用它们在对话内嵌入富交互审阅卡片（见 [review-ui.md](references/review-ui.md)）。
- 这些组件用于提升交互体验（如一键推导行文方案、按认知角色分组勾选主张、类 Word 修订模式改字批注），**没有强制的前置调用顺序限制**。
- 当环境没有这些工具时，直接在对话中与用户自然沟通并读写文件即可。

### 5. 机械辅助脚本（`<skill>/scripts/cta.py`）
脚本仅承担**纯机械的文本脱水、正则匹配与文件拼拆**，不控制主流程：
```bash
# 1. 将冗长的原始会话 JSONL 脱水为纯文本，并标出疑似密钥
python3 <skill>/scripts/cta.py extract --jsonl 会话.jsonl --coverage coverage.json --out 抽取.md --secrets-out secrets.json

# 2. 用共享+私有词表扫描正文中的禁用套话（ban）与观察句式（watch）
python3 <skill>/scripts/cta.py lint --article articles/<slug> [--block b001]

# 3. 按大纲将 blocks/*.md 编译为带锚点的工作稿 article.md，或通过导出守卫生成干净的分享包 export/
python3 <skill>/scripts/cta.py compile --article articles/<slug> [--export]

# 4. 当用户在 article.md 中直接改了文字时，按 <!-- block:id --> 锚点把改动拆回对应的 blocks/<id>.md
python3 <skill>/scripts/cta.py sync-anchors --article articles/<slug>
```

## 二、产物形态与目标约束（Target State & Invariants）

一篇文章默认存放在 `articles/<slug>/`（或用户指定的目录）。你可以直接用文件工具读写这些文件，也可通过 MCP UI 组件在用户提交时自动落盘：

```text
articles/<slug>/
  meta.json              # 文章元数据与钉住的 styleRevision
  writing-plan.json      # 写作动机（motivation）、文体、读者、目的、偏好轴、行文方案
  materials.json         # 已选会话与拥有完整正文的会话列表
  claims.jsonl           # 主张账本（每行一条事实或判断，含认知角色、来源与缺口提示）
  outline.json           # 章节结构（含每节回应的读者疑问、认知角色、关联主张、图位与块 id）
  preferences.jsonl      # 本篇从作者反馈中即时学到的写法偏好
  revisions.jsonl        # 块修订历史记录
  blocks/
    b001.md              # 块文件（YAML frontmatter + 正文，正文的唯一权威来源）
  figures/
    manifest.json        # 图记录清单（mermaid / drawio / svg-chart / raster / remote）
    fig-flow.mmd         # 图源文件
  article.md             # 带 <!-- block:id --> 锚点的工作稿（由 compile 生成）
  export/                # 最终可分享给读者的干净产物包（由 compile --export 生成）
    article.md
    figures/
```

### 核心约束（Invariants）
1. **真实材料与认知缺口显式化**：写进正文的主张必须来自经过核对的全文材料或用户补充材料（只有摘要的会话仅作线索提醒，不能脑补细节）。聊天中尚未验证的推断或缺失边界，记在 `writing-plan.json` 的 `knowledgeGaps` 或主张的 `gapNote` 中，在成文时显式补齐或限定边界。
2. **事实、结构与正文按块解耦**：
   - `blocks/<id>.md` 是正文的权威存储。
   - **局部修改默认只动被点名的那一块**：起草或改写某块时，只读取该块的 `claimIds`、前一块与后一块的只读文本（用于衔接语气）以及当前生效的风格偏好，**不要把整篇 `article.md` 塞进上下文重写**。
   - 除非作者明确要求「整篇重写」并二次确认，否则已接受的其他块保持原样（见 [revision.md](references/revision.md)）。
3. **单篇风格稳定与即时偏好沉淀**：
   - 每篇文章在 `meta.json` 中记录 `styleRevision`，篇内保持同一风格基线；全局 `profile.json` 升版只影响新文章。
   - 作者在审阅某块时给出的改字、批注或选版评价，应即时归纳为可推广的具体写法记入 `preferences.jsonl`，让下一块立刻生效（见 [preferences.md](references/preferences.md)）。
4. **视觉表达、多模态生图与图文协同（Figures & Multimodal Co-evolution）**：
   - **视觉触发与设计简报**：在痛点与输入输出（`hook`）、单步分数与掩码（`mechanism`）、文法能力对比或五层全景（`architecture`）处规划配图。生活类比图不能代替上面任何一张。先把 SVG 写到 `figures/` 并确认文件存在，再写相对路径；每张图下方附带图解框。不要把裸 `<svg>` 贴进正文当唯一图。详见 [figures.md](references/figures.md)。
   - **多模态生图与风格统一**：当用户在大纲（`review_outline`）、正文块（`review_block`）或图审阅（`review_figure`）中确认了 `raster` 配图，或在对话中要求生图时（`confirmed: true`），结合本篇锁定的 `visualStyle`（如 `tech-spotlight`、`whiteboard-sketch`、`editorial-comic`、`minimal-blueprint`）组装五要素 `prompt` 调用 `GenerateImage`；优先通过 `reference_image_paths` 传入首张已确认插图或个人范例样张以保持全篇画风一致，生图后立即用 `Read` 工具亲眼检视画面细节。
   - **看图写文、以图减文与双向迭代**：图负责展示同一输入的两种输出、一个机制步的前后状态，以及每一层各自不管什么。正文引出这一步的输入和状态，不把图上的每一格再抄一遍。图改了结构或结论时，把关联块标为 `stale` 并只改那一块（详见 [figures.md](references/figures.md)）。
5. **推演契约优先于空泛禁令**：科普体裁下，六幕、`mechanismTrace`、`capabilityContrast`、`acceptanceLayers` 与段间桥是硬字段。个人档案里的「段首直接给问题、不写铺垫」只禁止空泛总括，不能删掉使用场景、输入输出、状态、数值、能力对比和结尾回顾。局部修订仍只改被点名的块，但该块的 `bridgeFromPrev` 必须重写，并读相邻块的全文。
6. **干净的分享包（`export/`）**：
   - 交付给读者的 `export/` 不含块锚点、不含会话 ID、不含未脱敏的密钥（`sk-...` 等），且所有被大纲引用的块和图均已就绪、无 `ban` 级禁用套话。

## 三、推荐路径（Recommended & Flexible Paths）

以下路径是**弱约束的推荐实践**，请根据用户的指令和手头材料灵活裁剪、跳步或组合：

### 路径 A：从追问对话整理新文章（以写促学完整路径）
适合用户给了一段或多段探索性聊天，希望梳理成一篇有深度、好读的文章：
1. **还原动机与六幕**：阅读对话中的用户提问序列，提炼 `motivation`，并写成六幕，顺序固定为三层：开篇先落在读者正在做的事上，再写一次翻车与短清单；接着是没有掩码的逐词生成，并说明按格式输出在原理上站不住；然后是掩码、状态机各自成段，以及文法引擎上的工程优化；再用「第一步的允许集合如果本来就很大」那句问话进入语法不等于答案；最后是五层收束加一句黑体判断（详见 [writing-plan.md](references/writing-plan.md)、[discovery-questions.md](references/discovery-questions.md)）。可调用 `review_writing_plan`；方向不明时才用 `ask_questions`，一次只问会改变讲解顺序的分岔。
2. **梳理认知链式主张**：从全文材料中抽取核心主张写入 `claims.jsonl`，按 `friction` / `insight` / `evidence` / `boundary` 归类。默认把主张摘要写进写作计划的快审稿，不单独调用 `review_claims`。只有密钥未处理、事实对不上，或作者点了诊断芯片时，才打开主张审阅。
3. **规划读者认知大纲**：将六幕展开为 `outline.json`。每节标题 12～22 字，判断写在该节第一句。同时写 `readerQuestion`、`bridgeFromPrev`、`hookToNext`。开篇安排痛点与输入输出反差图，末节安排五层全景。默认不单独调用 `review_outline`，除非作者要改结构。
4. **成稿快审**：按块起草。科普默认笔调用 `tech-blogger` 的推演契约，不要为了选文风先跑一轮 `review_variants`。用 `review_block` 给作者读开篇和点了芯片的块。图随块看；只有 raster 需要亲眼看画面，或作者说图没有冲击力时，才调用 `review_figure`。
5. **词表检查与导出**：运行 `cta.py lint` 修正命中的禁用套话。观察级的明喻起手式如果出现在机制算完之前，改写成这一步的输入、状态和数值；机制之后的半句可以留下。风格候选默认不打断成稿，作者要求沉淀时再调用 `review_style_candidates`。最后 `cta.py compile --article ... --export`。

### 路径 B：材料与结构已成型，快速成稿
适合用户已经给出了清晰的提纲、成熟观点或结构化笔记，希望快速成文：
- 直接将用户给出的方向与论点整理写入 `writing-plan.json`、`claims.jsonl` 和 `outline.json`，跳过冗余盘问，直接进入按块起草与审阅。

### 路径 C：局部修订已有文章（改一段 / 改一句话 / 重画一张图）
适合文章已有初稿或成品，用户只想调整局部（详见 [revision.md](references/revision.md)）：
- 若用户在外部编辑器里直接改了带锚点的 `article.md`，先运行 `cta.py sync-anchors --article ...` 将改动收回对应块。
- 若用户点名改某一段或某句话，只读取目标块 `blocks/<id>.md`（及相邻块只读上下文），修改后写回或调用 `review_block` 让用户确认，最后重新 `compile`。
- 若用户修改或推翻了某条主张，更新 `claims.jsonl` 并将引用该主张的块标为 `stale`，仅针对受影响的块复核重写。

### 路径 D：学习与维护个人风格 / 词表
- 当用户提供过往旧文希望学习笔调时，直接阅读旧文归纳其人称、句式节奏、段落组织、开头习惯与代表性范文片段，经用户确认后更新 `~/.chat-to-article/profile.json`（详见 [style.md](references/style.md)）。
- 当用户指定禁用词或习惯用语时，直接更新 `~/.chat-to-article/lexicon/private.json`（详见 [lexicon.md](references/lexicon.md)）。
